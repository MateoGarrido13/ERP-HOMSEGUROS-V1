
### ADR-002: Orquestación de APIs Externas mediante Agregadores y Capa Anticorrupción

**Estado:** Aceptado
**Fecha:** 13 de Noviembre de 2026

**Contexto y Planteamiento del Problema**
El `Servicio 1` requiere consolidar información proveniente de múltiples `Proveedores` de APIs externas en paralelo para formar una respuesta unificada. Cada proveedor exige parámetros distintos, devuelve estructuras JSON diferentes y presenta tiempos de respuesta (latencia) y tasas de error variables. Permitir que la lógica central del `Servicio 1` negocie directamente con estas APIs y maneje sus errores acoplaría el dominio a sistemas inestables de terceros. ¿Cómo integramos múltiples proveedores externos manteniendo la consistencia semántica y garantizando la alta disponibilidad del sistema interno?

**Impulsores de la Decisión (Decision Drivers)**

* **Disponibilidad (Availability):** Un fallo en el `Proveedor A` no debe colgar los hilos de ejecución del servidor local ni impedir que se devuelvan los datos del `Proveedor B`.
* **Consistencia (Consistency) / Modificabilidad:** El `Servicio 1` debe trabajar con un único modelo de datos (Lenguaje Ubicuo), independientemente de las divergencias técnicas de los proveedores.
* **Rendimiento (Performance):** Las llamadas a la red deben ejecutarse concurrentemente.

**Opciones Consideradas**

1. Llamadas directas y secuenciales desde el Servicio a cada API.
2. **Patrón Scatter-Gather (Agregador) con Capas Anticorrupción (ACL) y Circuit Breaker.**
3. Un único mega-adaptador (God Object) compartido para todos los servicios que consumen al mismo proveedor.

**Decisión Tomada**
Elegimos la **Opción 2**. Implementaremos una estructura táctica compuesta por tres elementos:

1. **Agregador por Servicio (Scatter-Gather):** El `Servicio 1` instanciará sub-rutinas (hilos paralelos) para consultar a cada proveedor simultáneamente y luego consolidará los resultados.
2. **Capa Anticorrupción (ACL) por Proveedor y por Servicio:** Intermediarios exclusivos que traducen el modelo de datos de un proveedor externo al modelo canónico requerido específicamente por el `Servicio 1`.
3. **Cliente HTTP Compartido con Circuit Breaker:** La infraestructura de red pura será aislada. Un cliente HTTP base por proveedor encapsulará el estado del Circuit Breaker (Abierto/Cerrado), Timeouts y reintentos, protegiendo al sistema (Fail-Fast) cuando el proveedor externo se degrade.

**Consecuencias Positivas**

* **Aislamiento de Fallos (Resiliencia):** Si un proveedor externo experimenta latencia extrema, el Circuit Breaker abrirá el circuito, liberando instantáneamente los hilos del servidor y permitiendo al `Servicio 1` responder con los datos parciales disponibles.
* **Cumplimiento del Principio de Inversión de Dependencias (DIP):** El `Servicio 1` dicta el contrato (Interfaz) de los datos que necesita; los ACLs adaptan a los proveedores para cumplir ese contrato.
* **Desacoplamiento Semántico:** Agregar, eliminar o cambiar la versión de la API de un proveedor solo impacta su respectivo ACL, dejando intacto el código del `Servicio 1`.

**Consecuencias Negativas**

* Aumento de la complejidad estructural: Introduce múltiples capas de indirección (Agregador -> ACL -> HTTP Client) para completar una única tarea lógica.
* Dificultad de depuración (Tracing): Al tratarse de peticiones asíncronas en paralelo (Scatter-Gather), seguir la traza de ejecución de un error requiere un buen sistema de *logs* estructurados y métricas.
