### ADR-001: Adopción del Estilo Arquitectónico en Capas (Layered Architecture)

**Estado:** Aceptado
**Fecha:** 13 de Noviembre de 2026

**Contexto y Planteamiento del Problema**
El sistema backend requiere procesar peticiones HTTP, aplicar reglas de negocio sobre entidades genéricas y persistir o consultar datos en una base de datos relacional. Si se mezcla el código de parseo HTTP, las validaciones de dominio y las consultas SQL en un mismo bloque o función, el sistema sufrirá de alto acoplamiento, baja cohesión y será difícil de probar automáticamente (unit testing). ¿Cómo debemos estructurar lógicamente el código para asegurar la modificabilidad y testeabilidad a largo plazo?

**Impulsores de la Decisión (Decision Drivers)**

* **Modificabilidad (Modifiability):** Capacidad de cambiar la base de datos o el motor de vistas sin afectar la lógica de negocio.
* **Testeabilidad (Testability):** Capacidad de probar la lógica de negocio (Servicios) aislando el entorno web y la persistencia (mediante mocks).
* **Separación de Responsabilidades (SoC):** Cada componente debe tener una única razón para cambiar.

**Opciones Consideradas**

1. Arquitectura Monolítica sin estructura formal (Big Ball of Mud).
2. **Estilo Arquitectónico en Capas (Layered Architecture).**
3. Arquitectura Hexagonal / Puertos y Adaptadores.

**Decisión Tomada**
Elegimos implementar un **Estilo Arquitectónico en Capas Estricto** dividido en tres niveles principales de abstracción:

1. **Capa de Presentación / Controladores (Router & Handlers):** Únicamente responsable de extraer parámetros de la petición HTTP, delegar al servicio correspondiente y formatear la respuesta (JSON o HTML).
2. **Capa de Lógica de Negocio (Services):** Contiene las reglas del dominio y orquesta las transacciones. No sabe nada de HTTP ni de sentencias SQL puras.
3. **Capa de Acceso a Datos (Data Access / Repositories):** Responsable exclusiva de interactuar con el motor de base de datos y mapear los resultados a estructuras en memoria.

**Consecuencias Positivas**

* Alta cohesión: Los cambios en el enrutamiento HTTP (Handlers) no rompen las consultas SQL.
* Intercambiabilidad: Permite el uso de herramientas generadoras de código para la capa de acceso a datos de forma aislada sin contaminar el dominio.
* Curva de aprendizaje suave para nuevos desarrolladores al ser un patrón ampliamente reconocido.

**Consecuencias Negativas**

* Genera cierta burocracia en el código (boilerplate): Una operación simple de lectura/escritura (CRUD) sin reglas de negocio requiere atravesar las tres capas, creando métodos "pasamanos".
