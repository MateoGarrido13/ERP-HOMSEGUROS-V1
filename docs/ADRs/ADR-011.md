### ADR-011: Servicio de dominio sin acceso directo a Supabase

**Estado:** Aceptado  
**Fecha:** 13 de Noviembre de 2026  
**Arraigado en:** ADR-001 (capa de Servicios no sabe de SQL ni HTTP), ADR-004 (Supabase como plataforma)

---

**Contexto y Planteamiento del Problema**

El prompt 04 inyecta `SupabaseClient` directamente en el constructor de `ServicioCotizacion` y lo guarda como campo de instancia para un "TODO persistencia diferida". ADR-001 establece que la capa de Servicios "No sabe nada de HTTP ni de sentencias SQL puras" y que la capa de Acceso a Datos (Repositories) es "Responsable exclusiva de interactuar con el motor de base de datos". Acoplar `SupabaseClient` al servicio rompe el layered architecture estricto y expone al servicio capacidad de lectura/escritura irrestricta sobre BD (posiblemente con `service_role` que saltea RLS).

**Impulsores de la Decisión**

* **Separación de responsabilidades:** el servicio de dominio no debe conocer el cliente de BD.
* **Seguridad:** evitar que el servicio tenga credenciales de admin sobre la BD.
* **Testeabilidad:** el servicio debe poder probarse con un repository mockeado, no con un SupabaseClient real.

**Opciones Consideradas**

1. El servicio depende de un puerto de repository (interfaz) inyectado; `SupabaseClient` vive solo en el repository/adaptador de la capa de Acceso a Datos.
2. El servicio almacena `SupabaseClient` y lo usa directamente (estado actual del prompt 04).
3. El servicio no persiste nada; la persistencia vive exclusivamente en el handler/orchestrator.

**Decisión Tomada**

Se adopta la **opción 1**. `ServicioCotizacion` no almacena `SupabaseClient`. Recibe un puerto de repository (interfaz) para persistencia de cotizaciones (método `registrarCotizaciones` con `// TODO persistencia diferida`). La implementación concreta del repository (que usa `SupabaseClient`) vive en la capa de Acceso a Datos, separada del servicio. El `SupabaseClient` se inyecta en el repository, no en el servicio.

**Consecuencias Positivas**

* Cumple ADR-001 (servicio no sabe de SQL/Supabase).
* El servicio puede probarse con repository mockeado.
* No expone credenciales de BD al servicio de dominio.

**Consecuencias Negativas**

* Requiere definir la interfaz de repository (pendiente de especificación).
* El prompt 04 debe corregirse para quitar `SupabaseClient` del constructor del servicio.
