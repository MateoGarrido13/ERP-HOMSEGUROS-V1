### ADR-004: Plataforma Supabase y hub de aseguradoras en Edge Functions

**Estado:** Aceptado
**Fecha:** 13 de Noviembre de 2026
**Cierra:** spike ERP-9

**Decisión**

Supabase es la plataforma: PostgreSQL, Auth y Edge Functions. El hub de APIs de aseguradoras corre en Edge Functions (TypeScript/Deno), aislado como módulo de integraciones: ACL por compañía más Aggregator (scatter-gather). El fan-out v1 usa `Promise.allSettled` y `AbortController` con timeout de **4 segundos** por aseguradora. Go entra el día que ese Aggregator, con circuit breaker, sea un cuello de botella **medido**, no anticipado.

**Contexto y Planteamiento del Problema**

Hace falta un runtime para llamar en paralelo a las APIs de las compañías, traducir sus respuestas a un modelo canónico y devolver una comparativa parcial si alguna no llega a tiempo. El spike ERP-9 dejaba abierta la base y el proveedor de autenticación. Un backend Go para el Aggregator se consideró por concurrencia, pero la latencia dominante es de red (esperar a la aseguradora), no de CPU.

**Impulsores de la Decisión (Decision Drivers)**

* **Casos de uso E2E pronto:** el walking skeleton del multicotizador (CU-18 y afines) tiene que funcionar contra aseguradoras reales, no esperar un servicio Go.
* **Aislamiento:** el caos de las APIs de terceros no entra al dominio ni a `front/`.
* **Timeout de negocio:** 4 s por compañía; la comparativa sigue con las que respondieron (CU-18 `3b` «Sin respuesta»).
* **Costo de un cambio de lenguaje:** no se cambia el runtime por performance no medida.

**Opciones Consideradas**

1. Backend Go desde el día uno para el Aggregator (fan-out + circuit breaker).
2. Llamadas a aseguradoras desde `front/` o desde el prototipo.
3. **Supabase como plataforma; Edge Functions TypeScript/Deno para el módulo de integraciones.**

**Decisión tomada (detalle)**

Elegimos la **opción 3**.

| Pieza | Runtime |
| --- | --- |
| Base de datos | PostgreSQL en Supabase |
| Autenticación | Supabase Auth, detrás de las interfaces de `front/src/lib/` |
| Hub de aseguradoras | Edge Functions (TypeScript/Deno): ACL + Aggregator |
| Fan-out y timeout v1 | `Promise.allSettled` + `AbortController`, 4 s por aseguradora |
| Presentación | Next.js en `front/` |
| Go | Recambio del Aggregator **si** el fan-out concurrente a N compañías con circuit breaker se vuelve un cuello medido |

El patrón Aggregator + ACL sigue siendo ADR-002. El Circuit Breaker de ADR-003 queda **diferido**: v1 se sostiene con el timeout de 4 s y respuesta parcial.

**Fuera de este ADR**

Contrato HTTP del hub, layout de `supabase/functions`, y extraer el cliente Mercantil de `prototype/`. Eso exige spec aprobada ([guía spec-driven](../guia-spec-driven.md)) antes de código.

**Consecuencias Positivas**

* ERP-9 queda cerrado: Postgres, Auth y Edge Functions son un solo proveedor.
* El timeout de 4 s cubre el caso «compañía lenta» sin circuit breaker.
* `front/` no habla con las APIs de las compañías; el prototipo sigue siendo UX, no el hub.

**Consecuencias Negativas**

* Un circuit breaker real (y un Aggregator en Go) se pospone hasta haber métricas; un proveedor degradado seguirá consumiendo el presupuesto de 4 s hasta entonces.
* Auth y datos reales de Supabase todavía no están cableados en `front/`; la decisión no reemplaza esa implementación.
