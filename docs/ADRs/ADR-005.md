### ADR-005: Layout y contrato HTTP de supabase/functions

**Estado:** Aceptado  
**Fecha:** 13 de Noviembre de 2026  
**Arraigado en:** ADR-004 (Supabase + Edge Functions)

---

**Contexto y Planteamiento del Problema**

ADR-004 deja fuera de sí el "Contrato HTTP del hub, layout de `supabase/functions`", exigiendo spec aprobada antes de código. La cadena de prompts 00–10 define el layout bajo `supabase/functions/cotizar/` y `supabase/functions/_shared/`, con un endpoint `POST /cotizar` que devuelve 405/400/501/200. Sin un contrato HTTP acordado, cada prompt define códigos y cuerpos de forma inconsistente (ej. 501 usa `{ "error": "not implemented" }` mientras 400 usa `AppError` con `code`).

**Impulsores de la Decisión**

* **Consistencia:** todos los handlers del hub deben devolver el mismo envelope de error.
* **Especificación primero:** el layout y contrato deben aprobarse antes de implementar (requisito de ADR-004).
* **Seguridad del borde:** los endpoints expuestos al front (Next.js) necesitan CORS y cabeceras HTTP correctas.

**Opciones Consideradas**

1. Definir el contrato HTTP y layout en este ADR ahora.
2. Dejar cada prompt que defina su propio contrato (riesgo de inconsistencia).
3. Postergar hasta que exista una spec formal separada (retrasaría la cadena 01–09).

**Decisión Tomada**

Se adopta la **opción 1**. Layout:

```
supabase/functions/
  _shared/
    types.ts          — SolicitudCotizacion, CotizacionCanonica, IProveedorACL, ICircuitBreaker, AppError, CircuitBreakerOpciones
    circuitBreaker.ts — CircuitBreakerImpl, circuitBreakerRegistry, getOrCreateCB
    httpClient.ts     — HttpClient (post<T> con fetch + signal + CB)
  cotizar/
    index.ts          — entry point Deno.serve, routing POST /cotizar -> handler
    handler.ts        — handleCotizar (405/400/501, validación DTO)
    servicio.ts       — ServicioCotizacion (delegación a Orquestador)
    orquestador.ts    — Orquestador (fan-out Promise.allSettled + AbortController 4 s)
    acl/
      mappers/
        sancor.ts     — SancorACL (sin HTTP directo)
        stub.ts       — StubACL (walking skeleton, sin red)
```

**Contrato HTTP (envelope de errores):**
* `405 Method Not Allowed` — `{ "error": { "code": "METODO_NO_PERMITIDO" } }`, cabecera `Allow: POST`.
* `400 Bad Request` — `{ "error": { "code": "BODY_INVALIDO" | "SOLICITUD_INVALIDA" } }`, sin stack ni detalles internos.
* `501 Not Implemented` — `{ "error": { "code": "NOT_IMPLEMENTED" } }` (temporal, walking skeleton).
* `200 OK` — array de `CotizacionCanonica[]`.
* Todas las respuestas JSON con `Content-Type: application/json`.
* CORS: origen permitido desde variable de entorno; sin `*` en producción.

**Regla:** ningún prompt de la cadena 01–10 modifica este contrato sin actualizar este ADR.

**Consecuencias Positivas**

* Consistencia entre handlers (mismo envelope, mismos códigos).
* El criterio `deno check` de cada prompt tiene un contrato estable contra el cual compilar.
* CORS y cabeceras definidas antes de exponer el endpoint al front.

**Consecuencias Negativas**

* Aumenta la burocracia inicial (hay que aprobar el layout antes de código).
* El 501 es intencionalmente temporal; habrá que reemplazarlo cuando se implemente el servicio real.
