### ADR-003: Implementación del Patrón Circuit Breaker para integraciones con APIs externas

**Estado:** Aceptado (implementación diferida; ver ADR-004)
**Fecha:** 13 de Noviembre de 2026

El patrón Circuit Breaker sigue adoptado. **No se implementa en v1.** El hub arranca en Edge Functions TypeScript con timeout de 4 s (`AbortController`) y comparativa parcial; el breaker entra cuando el Aggregator sea un cuello **medido**, no anticipado. Runtime y aplazamiento: [ADR-004](ADR-004.md). Las «goroutines» del contexto de abajo no son el runtime actual.

**Contexto y Planteamiento del Problema**
El sistema se integra con APIs de terceros a través de clientes HTTP para nutrir la capa de servicios. Estos sistemas externos están fuera de nuestro control y son susceptibles a interrupciones, picos de latencia o caídas totales. Si nuestra aplicación intenta comunicarse continuamente con un proveedor degradado, los hilos de ejecución (goroutines) se bloquearán esperando el *timeout* HTTP en cada petición. Esto no solo degrada la experiencia del usuario, sino que puede provocar el agotamiento de recursos locales (Resource Exhaustion) y una falla en cascada que tumbe nuestro propio servidor. ¿Cómo protegemos los recursos de nuestra aplicación frente a fallos prolongados en dependencias externas?

**Impulsores de la Decisión (Decision Drivers)**

* **Disponibilidad (Availability) y Tolerancia a Fallos:** El sistema local debe mantenerse operativo incluso si una o más dependencias externas fallan.
* **Fallo Rápido (Fail-Fast):** Es preferible rechazar o abortar una operación inmediatamente antes que mantener los hilos bloqueados durante segundos esperando un fallo inminente.
* **Gestión de Recursos (Performance):** Prevenir la saturación de conexiones de red y memoria por peticiones encoladas.

**Opciones Consideradas**

1. Depender exclusivamente del *Timeout* estándar del cliente HTTP.
2. Implementar únicamente un patrón de Reintentos (Retry with Exponential Backoff).
3. **Implementar el Patrón Circuit Breaker (Cortocircuito) envolviendo el Cliente HTTP.**

**Decisión Tomada**
Elegimos la **Opción 3**. Se integrará un **Circuit Breaker** a nivel de infraestructura, específicamente dentro del Cliente HTTP Base que utilizan las Capas Anticorrupción (ACL).

* **Circuito Cerrado:** Las peticiones fluyen normalmente. Si los errores o *timeouts* superan un umbral predefinido (ej. 50% de fallos en 10 segundos), el circuito se abre.
* **Circuito Abierto:** Las peticiones se abortan inmediatamente devolviendo un error interno (Fail-Fast) sin realizar la llamada de red.
* **Circuito Medio-Abierto:** Tras un tiempo de gracia, se permite el paso de una cantidad limitada de peticiones de prueba para verificar si el proveedor externo se ha recuperado.

**Consecuencias Positivas**

* **Prevención de Fallos en Cascada:** Al cortar de raíz las peticiones hacia un servicio degradado, el servidor libera instantáneamente sus hilos de ejecución, permitiendo que el Agregador (Scatter-Gather) devuelva resultados parciales sin penalizar el tiempo de respuesta del usuario final.
* **Auto-recuperación:** El estado "Medio-Abierto" permite que el sistema se reconecte automáticamente con el proveedor una vez que este resuelve sus incidentes, sin intervención manual de operaciones.

**Consecuencias Negativas**

* **Complejidad de Configuración:** Requiere un análisis cuidadoso y pruebas de carga para afinar los umbrales de disparo (volumen de fallos, tiempos de gracia, latencia máxima). Configuraciones muy sensibles abrirán el circuito ante falsos positivos, mientras que configuraciones muy laxas anularán su propósito.
* **Opacidad sin Monitoreo:** Si los cambios de estado del Circuit Breaker (Apertura/Cierre) no emiten alertas y *logs* estructurados, el equipo de desarrollo no se enterará de que el sistema está operando en modo degradado.
